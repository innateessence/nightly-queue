# Vibearr release acceptance

The source implements a four-container, Docker-only issue-to-PR factory. The
minimum live release is two genuine dependent source tasks: a selected provider
implements A, trusted checks/reviews pass, a human merges A, then B starts from
that verified merge and follows the same process. No command or plan approval
prompt is required inside a configured project's registered policy.

Engineering qualification and live acceptance are separate. Keep processing
disabled until the actual worker boot and selected provider/account/model are
accepted. Authentication files, version output, protocol fixtures, unit tests and
older source/image/boot reports cannot establish readiness.

Required engineering evidence binds exact committed source, all four immutable
service images and observed container identities, current authenticated worker
boundary/role permission proof, and eight real proof documents:

- resource limits and responsive control under actual pressure;
- worker restart and original-operation reconciliation;
- runner restart and durable controller recovery;
- changed-dependency execution;
- image-owned trusted candidate validation;
- actual source-bound browser PNGs;
- offline CLI/runner/executor distribution packaging;
- quiescent backup/restore with fresh restored authority.

The full harness observes the same four container IDs through startup, boundary,
dependency, candidate, browser and pre-backup phases. Protected canonical hashes,
source/image identities and original response envelopes are verified. A fixture
flag or missing raw proof cannot be overridden by a successful summary.

Live acceptance additionally needs selected account authentication and renewal,
real native sessions, both genuine human merges, actual failure/check-repair and
review-repair paths, exhaustion, missing capability, cancellation, controller and
worker restart, and independent work during human review. Unsupported quota
telemetry stays unsupported; never label it unlimited.

The [acceptance observer](factory-acceptance.md) collects finite, resumable,
read-only observations. It cannot start paid work, publish issues, merge PRs,
change protection rules or enable execution. Missing evidence keeps its report
unqualified. Live provider renewal and human-merge acceptance remain pending
until genuine current evidence is supplied.

Humans merge every PR. Automatic merging and deployment require a separate
explicitly approved rollout and are not authorized by engineering qualification.
